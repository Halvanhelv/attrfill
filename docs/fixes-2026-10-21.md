# Fixes and re-check — 21 October 2026

Stage: a working MVP for the pilot with mandatory review of risky fields. The end-to-end scenario passes; extraction quality and labour savings still need confirmation on new data.

## What was fixed

- The brand and model of a compatible device no longer become attributes of an accessory via rules, NER or LLM. The accessory's own brand is kept.
- The strict policy `2026-10-21-pilot` requires a confidence of at least 0.98. Model, colour, all laptop fields and the undetermined category require a human. The setting lives in `config/acceptance.yml` and does not depend on the directory of trained weights.
- Reference-catalog suggestions with an unconfirmed brand/model pair give no grounds for automatic publication. Typical category values are not published on their own either.
- The downloadable CSV neutralizes formulas with an apostrophe. JSON and the programmatic CSV export keep exact values.
- Normalization of strings with binary encoding was fixed. The interface explains mandatory review; reports and the API state the policy version.

## Quality and the cost of limiting risk

Comparison on the same 831 cards and 4,245 labelled values, with the same frozen weights, without LLM. TRAIN is 4,169 cards; families are separated heuristically. The data was used during development, so this is diagnostics, not an independent blind test. Partial labelling does not allow all output values to be assessed.

| Metric | Before | After |
|---|---:|---:|
| Macro-F1 | 0.581 | 0.580 |
| Accepted automatically | 1,900 (44.8%) | 794 (18.7%) |
| Accepted correctly | 1,849 | 791 |
| Errors among accepted | 51 | 3 |
| Accepted precision | 97.3% | 99.6% |
| Requires review | 1,664 (39.2%) | 2,758 (65.0%) |
| Not found | 681 (16.0%) | 693 (16.3%) |

The precision of admission to publication went up; extraction quality itself barely changed. The reduction in errors was achieved mainly by reducing automation. The three remaining discrepancies are the brand Xiaomi instead of Redmi. The overall 99.6% precision on this sample does not prove that precision for each filter and is not a guarantee for new cards.

On 120 synthetic accessory cards, F1 rose from 0.486 to 1.000, and accepted precision from 0.491 to 1.000. This is a narrow regression set. In the final check of unknown categories all values were routed to a human: the absence of automatically accepted errors here does not mean successful automation.

## What remains before rollout

We need new independent labelling, a check of the popular filters one by one, and a measurement of operator time given that 65% of values go to review. The economics calculator gives scenario estimates, not proven savings. The current run without LLM does not confirm its usefulness; the no-LLM mode remains the main one. Performance on the target Linux / 2 CPU / 4 GB is not yet confirmed; the earlier speed promises in the README have been replaced by a measurement that states the environment.

Already saved results are not recalculated automatically: cards must be reprocessed for the new policy.
